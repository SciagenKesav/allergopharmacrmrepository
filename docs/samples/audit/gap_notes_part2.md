## 1. High-risk area #2: the license model

**The license model is per-Account, not per-Address, and there is no Address object at all today.** `find force-app/main/default/objects -iname "*address*"` returns no results — Sciagen's data model has never had an Address child entity for `Sciagen_Account__c`. All licensing fields (`License_Number__c`, `License_Expiry_Date__c`, `License_Verification_Status__c`, `Medical_Council_Reg_Number__c`, `Controlled_Substance_License__c`) live flat on `Sciagen_Account__c` itself (`force-app/main/default/objects/Sciagen_Account__c/fields/*.field-meta.xml`), one value per HCP account regardless of how many states or practice locations that HCP has. Address is likewise flat on the account (`Billing_Street__c/City__c/State__c/Postal_Code__c/Country__c`, per the Part-1 inventory §1.1), not a separate object with its own license fields. On the iOS side, the `HCP` struct (`Models/Models.swift:126-198`) mirrors this exactly: one flat `licenseNumber` field and flat address fields, no `Address` type anywhere in the codebase. This is a direct **CONFLICT** with spec SM-LIC-01, which requires per-Address licensing so an HCP practicing in multiple states can hold a distinct, independently-tracked license per state.

**There is a status lifecycle, but it does not match the spec's New/Sampled/Valid/Expired/Invalid model.** `Sciagen_Account__c.License_Verification_Status__c` is a picklist with values `Unverified` (default), `Verified`, `Invalid`, `Expired`, `Pending` (`fields/License_Verification_Status__c.field-meta.xml`). Two of the spec's five required values are simply absent: there is no `New` value (which would mark an unvalidated HCP eligible for a one-time drop) and no `Sampled` value (which would mark that one-time drop as used and block further sampling until vendor validation) — the entire one-time-sample-drop concept (SM-LIC-09/10/15/16) is unimplemented. `Verified` functions as the spec's `Valid`, and `Expired`/`Invalid` map directly and are genuinely enforced: `SampleEligibilityService.cls:104` blocks sampling for any status other than `Verified`, and `HcpLicenseExpiryBatch.cls` (a real `Database.Batchable<SObject>, Schedulable` job, scheduled daily at 00:30 via its `schedule()` method) flips `Verified` → `Expired` once `License_Expiry_Date__c` passes. A `Sample_Eligible__c` formula field (`AND(ISPICKVAL(License_Verification_Status__c,'Verified'), NOT(ISBLANK(License_Expiry_Date__c)), License_Expiry_Date__c>=TODAY(), Can_Prescribe__c)`) is a genuinely reusable, close analogue of the spec's "License Valid To Sample" formula (SM-LIC-07) — it just needs to move from Account to Address and gain a grace-period branch.

**There is no propagation logic across same-state addresses, because there is nothing to propagate across.** A targeted search for an `AddressLicenseService` class (or any equivalently-named service) found nothing, and none of the copy-on-create / delete-cascade / update-cascade behaviors required by SM-LIC-17/18/19/20 exist in any form, on either the server or the iPad client. This is not a partial gap — it is a complete absence, entirely blocked on the Address object not existing yet.

**Net effect:** SM-LIC-01 is the root-cause conflict behind roughly two-thirds of this scope's MISSING/CONFLICT findings (SM-LIC-04 through SM-LIC-20, plus SM-CS-01/02's state/DEA fields, which the spec explicitly places on Address in section 3.9). Building the Address object and migrating existing license data onto it should be sequenced first; most of the rest of §7's requirements are then straightforward extensions of logic that already exists in a reusable (if Account-scoped) form.

## 2. Data migration needs

- **Move `Sciagen_Account__c` license fields to the new Address object.** Org data confirms 41 of 152 `Sciagen_Account__c` records currently have `License_Number__c != null` (per `01_inventory_salesforce.md` §1.1) — these need a migration path onto per-address rows (likely: create one Address record per account carrying its current billing-state address, and move the license fields onto it), not a from-scratch build.
- **`License_Verification_Status__c` values need remapping**, not just copying: `Unverified` → new `New`/`Pending` semantics need to be decided (the spec's `New` specifically means "eligible for a one-time drop," which `Unverified` today does not confer), and a decision is needed on whether `Pending` (an existing value with no citied usage found in Apex) is retired or kept.
- **iOS local cache/blob migration**: `UserDataStore`'s single JSON blob (per `02_inventory_ios.md` §2) currently embeds `HCP.licenseNumber` flat; once the server model changes to per-address licensing, the local model, its `UserDefaults` blob schema, and the migration logic in `UserDataStore.load()` (which already has precedent for blob-version migration per the iOS inventory) will all need a version bump and a migration path for any signed-in device with stale cached data.
- No `Sample_State_Setting__c`/`Sample_State_Credential_Setting__c`/`Account_Authorization__c`/DEA/CDS data exists anywhere today (confirmed absent by directory search), so those are pure net-new builds with no legacy data to migrate.

## 3. Breaking-change items

- **Renaming/remapping `License_Verification_Status__c` picklist values** (to add `New`/`Sampled` and align `Verified`→`Valid` naming, per SM-LIC-09/10/11) is a breaking change for anything reading the current values — notably `HcpLicenseExpiryBatch.cls` (hardcoded string comparisons `'Verified'`/`'Expired'`) and `SampleEligibilityService.cls` (hardcoded `!= 'Verified'` check) both need simultaneous updates, or a transition window where both old and new values are tolerated.
- **Moving license fields off `Sciagen_Account__c` onto a new Address object** is a breaking change for the formula field `Sample_Eligible__c` (which lives on Account and reads Account-level license fields) and for any report, list view, or LWC that currently surfaces `Sciagen_Account__c.License_Number__c`/`License_Expiry_Date__c`/`License_Verification_Status__c` directly — none of those consumers were enumerated in this pass beyond the classes read, so a full "who reads these fields" sweep is recommended before removing them from Account (versus keeping them as denormalized/rollup convenience fields alongside the new Address-level source of truth).
- **`SampleTransactionService.cls:143` and `SampleEligibilityService.cls:54-57`** (the SM-CS-06 hypnotic/sedative/tranquillizer block) both key off `Product__c.Is_Restricted__c`/`Restriction_Reason__c` — if the Sample Management build renames these to the spec's `Therapeutic_Restriction__c` (SM-PRD-04), both call sites must be updated together or the block silently stops working.

## 4. Offline/online rule-parity gaps (within this scope)

- **SM-CS-03 (signature required for controlled substances) is fully enforced on the server** (`SampleDropService.cls:33,161-169` blocks submission of a call with an unsigned controlled-substance line, independent of opt-in status) **but has zero client-side awareness.** The iOS `ProductCatalogItem` model carries no `Is_Controlled_Substance__c`/`Requires_Signature__c` field at all, and the CVR's "Capture Signature" action is a boolean-flag append with no gating logic (`Views/CLMViews.swift`, confirmed in the iOS inventory §5.2/§6). A rep could fill out a controlled-substance sample line offline, believe the call is complete, and only discover the rejection when the device syncs — the server-side fail-safe the spec calls for in section 0 item 5 works, but the "clear, recoverable error" UX it also calls for does not yet exist, because the client can't even recognize the line as controlled to explain why it was rejected.
- **SM-CS-06 (hypnotic/sedative/tranquillizer hard block) has the same shape of gap**: solidly enforced server-side at two points (eligibility check and transaction service), but the iOS `SampleDrop`/`ProductCatalogItem` models carry no `Is_Restricted__c`/`Restriction_Reason__c` field and the sample-add UI has no corresponding check — only an unrelated, hardcoded 3-product yearly cap exists client-side (`Services/CLMData.swift:20-32`). An offline rep can stage a restricted-product line with no warning.
- **The entire Mid-Level Practitioner / Authorized Receiver / License-status area (SM-LIC, SM-MLP, SM-CS) has no shared rules-engine today on either side** — there is no Swift rules engine mirroring `SampleEligibilityService.cls` logic at all (confirmed: the only client-side "rule" found in this scope's territory is the hardcoded yearly-cap check), so spec requirement SM-IOS-03 ("shared Swift rules engine mirroring server rules... contract tests run the same JSON fixtures against Apex and Swift") is a from-scratch build, not an extension, for every rule this scope covers.

## 5. Top reusable pieces / top gaps

**Most surprisingly reusable (top 4):**
1. `SampleEligibilityService.cls` and `SampleTransactionService.cls`'s hypnotic/sedative/tranquillizer block (SM-CS-06) — genuinely hard-blocks at two independent enforcement points with a UCPMP clause citation baked into the error message, plus audit logging via `Sample_Blocked_Attempt__c`. This is close to production-ready and should be extended, not replaced.
2. `HcpLicenseExpiryBatch.cls` — a correctly-written, already-scheduled daily batch doing exactly the Valid→Expired transition the spec asks for (SM-LIC-14); only missing the rep-notification step.
3. The `Sample_Eligible__c` formula field — a working, close analogue of the spec's "License Valid To Sample" formula (SM-LIC-07) that can likely be ported almost as-is once it targets Address instead of Account.
4. The controlled-substance signature gate (SM-CS-03) in `SampleDropService.cls` — correctly independent of the opt-in/consent system, correctly blocks at call submission, and correctly distinguishes per-line `Needs_Signature__c` from the call-level `Signature_Captured__c` flag.

**Worst gaps/conflicts (top 5):**
1. **SM-LIC-01** — no Address object exists at all; license is Account-scoped everywhere, blocking most of §7 (CONFLICT, XL effort, root cause for ~20 of the 37 IDs).
2. **SM-MLP-01 through SM-MLP-10** — the entire mid-level-practitioner/collaborative-relationship/DEA-validation subsystem (`Account_Authorization__c`, `Sample_State_Credential_Setting__c`, supervising-physician picking and validation) is completely absent on both server and client; SM-MLP-08 alone (DEA checksum + dual-license + schedule matching) is an XL, high-dependency build.
3. **SM-CS-01/SM-CS-02** — no DEA or state CDS license modeling exists anywhere in the codebase; the only controlled-substance license check today is a single free-text field checked for blank/non-blank, with no expiry, no checksum, no per-state requirement.
4. **iOS has no licensing/eligibility/restriction rules engine at all** in this scope — every server-side rule surveyed above (license status, controlled-substance signature requirement, hypnotic/sedative block) has zero client-side mirror, which is a direct conflict with SM-IOS-03's "server-authoritative but iOS-mirrored" architecture principle stated in spec section 0.
5. **SM-MLP-11 / SM-CS-05 Authorized Receiver** — the one item in this scope with real partial groundwork (`Authorized_Recipient_Name__c`, `Handed_To_Prescriber__c` fields on `Sample_Transaction__c`), but the fields are inert: no Apex anywhere reads or validates them, they aren't split into first/middle/last name, and there's no `Account_Authorization__c` "Authorized Receiver" record type behind them at all — worth calling out because it's both the default jurisdiction's (IN-UCPMP) most directly-needed MLP-area item and currently the cheapest to close (Extend, M effort) of the group.
