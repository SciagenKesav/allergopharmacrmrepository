# Gap Analysis Notes — Part §2 slice (Calls-with-samples/e-signature/barcode, Sample opt-in, Additional features, Sample inventory counts)

Scope: SM-CALL-01..16, SM-BAR-01..09, SM-SIG-01..15, SM-OPT-01..12, SM-CC-01..07, SM-CT-01/02, SM-HV-01, SM-ALC-01..04, SM-IO-01..03, SM-INV-01..07 (76 IDs). Full requirement-by-requirement detail is in `docs/samples/audit/gap_matrix_part3.csv`. All citations below repeat the file:line evidence gathered in this pass; see the CSV for the complete per-ID trail.

## 1. High-risk area #3 — Signature capture & storage

The picture is better on the Salesforce schema than the spec's own benchmark-truncation warning implies, but the actual capture pipeline for **samples specifically** does not exist end to end on either platform.

**Format/size:** `Call_Visit_Report__c.Signature_Image__c` is a `Text(18)` field storing a `ContentDocument` Id (`force-app/main/default/objects/Call_Visit_Report__c/fields/Signature_Image__c.field-meta.xml`, description: "ContentDocument Id of the signature image") — this already sidesteps the spec's 32 KB long-text-area truncation warning by design, and is a genuinely reusable pattern (SM-SIG-06 PARTIAL, not CONFLICT). By contrast, `RCPA_Audit__c.Chemist_Signature__c` is a `LongTextArea(131072)` storing a base64 PNG data URL (`force-app/main/default/objects/RCPA_Audit__c/fields/Chemist_Signature__c.field-meta.xml`) — exactly the truncation-prone anti-pattern the spec warns against — and `Consent__c.Sample_Opt_In_Signature__c` again uses the safer ContentDocument-Id text pattern. **The Sample Management build should copy the ContentDocument pattern and must not copy the RCPA LongTextArea pattern.**

**Hashing:** no SHA-256/hash field exists anywhere in the org (`grep -ri "hash\|ledger" force-app/main/default` returns zero hits) — `Sample_Ledger_Entry__c` and any `Ledger_Hash__c`/`SHA256` field are entirely absent. This is a cross-cutting gap: without it, SM-SIG-06's tamper-evidence requirement and the disclosure/audit ledger (§15, out of my scope but referenced throughout §10-13) cannot be satisfied.

**Recapture/lock behaviour:** `Call_Visit_Report__c` has `Unlock_Request__c`/`Unlocked_At__c`/`Unlocked_By__c`/`Unlock_Count__c` fields and a working trigger (`SupportCallRelockTrigger.trigger` → `SupportUnlockService.afterCallSubmit`) — a real lock/unlock mechanism exists, but it is generic to call submission, not driven by signature capture specifically, and none of the four recapture-matrix branches (SM-SIG-12..15) or their config knobs (`Enable_Samples_On_Sign_Save`, `Enable_Samples_On_Save`, `Disable_Sign_Button`) exist anywhere.

**Where the image actually lives / who writes it:** nobody. `SampleDropService.cls:97-111` *reads* `CVR__r.Signature_Image__c`/`Signature_Captured_At__c`/`Signature_GPS__c` to snapshot them onto the resulting `Sample_Transaction__c`, but no Apex class was found that creates the `ContentVersion` in the first place (only test code hardcodes a fake Id: `SampleDropServiceTest.cls:61`). On iOS, the CVR's "Capture Signature" action is a one-line stub — `session.attachments.append(AttachmentRef(kind: .signature, label: "HCP signature captured"))` (`CLMViews.swift:1092-1094`) — no drawing surface, no image, no stroke data at all. The two *real* signature pads that do exist (`ConsentCaptureView.swift`'s `SignatureSheet`, `ConsentCaptureView.swift:406-488`, and RCPA's chemist pad) are DragGesture/Canvas-based, not PencilKit as the spec assumes, and neither enforces any minimum point-count or stroke-length (`canConfirm` at `ConsentCaptureView.swift:425-427` only checks `!strokes.isEmpty && attested && !name.isEmpty` — a single tap currently "signs"). Per the iOS inventory (§6), stroke data for both of those existing pads is **never actually pushed to Salesforce** — only signer name/meaning/timestamp metadata is sent (`SalesforceRestDataService.swift:1557-1559,1584`), so even the working pads don't close the loop to the `ContentDocument` field described above.

**Bottom line:** the receiving schema (ContentDocument-Id field) is sound and reusable; everything upstream of it — a real sample-specific signature UI, validation, the write path that actually creates the ContentVersion, hashing, and history-on-recapture — is missing.

## 2. High-risk area #8 — Remote signing

There is **no Experience Cloud, Salesforce Site, or any other guest-user-accessible surface anywhere in this org.** `force-app/main/default/experiences/`, `networks/`, `sites/`, and `digitalExperiences/` are all absent; the only "Sites"/"Community" references are the stock, unconfigured `standard__Sites.app-meta.xml`/`standard__Community.app-meta.xml` app-launcher tiles that ship with every org edition. This was independently re-confirmed in this pass (`find force-app -ipath "*sites*" -o -ipath "*experiences*" -o -ipath "*networks*"` → no matches beyond the standard app shells).

The schema *anticipates* remote signing — `Sample_Transaction__c.Signature_Type__c` has picklist values `In_Person`/`Remote_Link`/`Remote_QR` (`force-app/main/default/objects/Sample_Transaction__c/fields/Signature_Type__c.field-meta.xml`) — but nothing populates or consumes that value today (`grep -rln "Remote_Link\|Remote_QR" force-app/main/default` returns no matches in any class or trigger).

Consequently there is **no token signing, no expiry window, and no single-use enforcement** to evaluate — none of that infrastructure exists to be secure or insecure. Both SM-SIG-09 (Remote Sampling page) and SM-OPT-06/07/08/09 (remote opt-in link/QR) require building this from zero: a public guest-user Experience Cloud page or Salesforce Site, a signed single-use token scheme with server-side expiry, and (since `LocalNotificationService.swift` is confirmed local-only with no APNs entitlement or `didRegisterForRemoteNotifications` anywhere, per iOS inventory §6) a genuine server-initiated push channel does not exist either — "rep sees a confirmation (push + in-app)" per SM-OPT-08 currently has no push half at all. This is the largest single net-new build item in this slice (rated XL for SM-OPT-07 and SM-SIG-09 in the CSV).

## 3. Data migration needs spotted in scope

- **None of the sample-inventory objects have any data today** (`Sample_Lot__c`, `Sample_Transaction__c`, `Sample_Drop__c`, `Sample_Allocation__c`, `Sample_Limit__c` all return `COUNT(Id) = 0` per the Salesforce inventory §1), so there is no legacy sample data to migrate in this sandbox — but if a production org has live sample history in a prior system, none of the structures this slice depends on (`Sample_Inventory__c`, `Sample_Lot_Item__c`/TagAlert, `Rep_Roster__c`, `Inventory_Order__c`) exist yet to receive it.
- **`Consent__c` has only 4 records and `Consent_Product__c` has 0** — any bulk import of historical sample-opt-in consents will need the four missing fields (captured-by, valid-from, method flags, consent-text-version — see SM-OPT-04) added *before* a migration, or the imported rows will be structurally incomplete from day one.
- **Signature images**: since no ContentVersion-writing code path exists yet for CVR/sample signatures, any historical paper signature cards or scanned images (SM-CALL-16) would need a fresh ingestion pipeline built alongside the Sample_Card fallback feature itself (currently 100% absent).
- **Cold-chain / custom-text fields exist on `Sample_Transaction__c`/`Sample_Drop__c` but are absent from every UI that creates those records** (layouts and the `cvrSampleDrops` LWC add-form both expose only Product/Qty). Any data migrated into those fields directly (e.g., via Data Loader) would be silently invisible/uneditable to end users until the UI catches up — worth flagging to whoever owns a cutover plan.

## 4. Breaking-change items spotted in scope

- **Cold-chain sample lines are currently un-submittable through the only UI that creates them.** `SampleDropService.beforeInsert` (lines 51-56) hard-blocks any `Requires_Cold_Chain__c=true` product's line when `Cold_Chain_Tag_Number__c`/`Cold_Chain_Status__c` are blank, but the `cvrSampleDrops` LWC add-form (`cvrSampleDrops.html:19-22,52-53`) never renders those two fields. If any cold-chain product is marked `Requires_Cold_Chain__c=true` in production today, every attempt to log a sample of it through the web Call form will fail with a server error and no client-side explanation of what's missing — a real, live-user-facing breaking condition, not just a hypothetical future gap. Building the real cold-chain UI (SM-CC-01..07) fixes this rather than introducing a break, but it should be flagged as *currently broken*, not merely *not yet built*.
- **Sample_Allocation__c's own page layout is missing the majority of its fields** (`Period_Start__c`, `Period_End__c`, `Allocated_To_User__c`, `Allocated_To_Territory__c`, `Used_Quantity__c`, `Remaining_Quantity__c` are all absent from the layout XML, which shows only `Allocation_Quantity__c`/`Product__c`/`Status__c`/`Name`/`OwnerId`) — any admin trying to manage allocations via the standard record page today cannot actually set a period or a recipient. Introducing a proper Allocation LWC (SM-ALC-01..04) will change admin muscle memory but is not itself a regression since the current layout is already non-functional for the object's stated purpose.
- **Rebuilding the CVR "Capture Signature" stub into a real capture flow (SM-SIG-01..15) is a behavior change for any live users**, since today tapping it silently marks `signatureCaptured = true` with zero friction; a real capture flow with padlock/biometric-unlock/point-count validation will, correctly, add friction that did not exist before. Worth calling out explicitly in rollout communications, not just engineering docs.

## 5. Offline/online rule-parity gaps

This is the most consequential theme in this slice, because the build spec's rule #5 ("the iPad can never create a compliant-looking record that the server would reject") is **currently violated in the one place samples exist at all today**:

- **The sample-limit check that does exist is entirely client-side and cosmetic.** `UserDataStore.samplesUsedThisYear(hcpId:product:excludingCVR:)` (`UserDataStore.swift:663-669`) sums quantities only from CVRs already present in the on-device array — it does not call the server, and per the iOS inventory (§11.3) it can under-report (and therefore under-enforce) whenever the device's local history is incomplete (fresh install, sync gap, another rep/device sampling the same HCP). Worse: the over-limit flag on already-added rows is **display-only** (`CLMViews.swift:1050-1070`) — nothing gates `save()`/`submit()` on it, and the push payload for `Sample_Drop__c` sends only `CVR__c`/`Product__c`/`Qty__c` (`SalesforceRestDataService.swift:2446-2469`), giving the client no signal that the server even has an opinion. Meanwhile the *server-side* limit engine (`SampleLimitChecker.cls` + `SampleEligibilityService.check()`, invoked from `SampleDropService.beforeInsert`) is real, live, and can hard-block via `d.addError()` — so today's actual behavior is: **the app will let a rep believe a sample was successfully logged, and the server will silently reject it on sync**, with no evidence in this pass of the client surfacing that rejection back to the rep in a recoverable way. This is the textbook violation of the spec's own authoritative-server rule, and it already exists in the shipped app for the *unrelated, hardcoded 3-product* cap — it will only get worse once real `Sample_Limit__c` records and UCPMP 12-pack limits are turned on, unless SM-CALL-08/SM-SIG-12..14's sync-immediately-on-save design and clear rejection UX are built deliberately.
- **The FEFO lot-assignment and on-hand-quantity rules (SM-CALL-05/06) exist only server-side** (`SampleEligibilityService.cls` `lot()` helper) with **zero mirror on iOS** — there is no lot, no on-hand-quantity, no expiry concept in the client at all (confirmed by the iOS inventory's exhaustive grep for `Lot`/`Inventory`/`batch`/`expiry`). Today a rep has no way to know offline whether a sample can be disbursed at all until the server accepts or rejects the sync — there is no "mirror the rule on iPad for offline UX" happening yet for any lot-related rule.
- **Cold-chain breach-blocking (SM-CC-06) and hypnotic/sedative/tranquillizer blocking exist only server-side** with no client-side equivalent to warn the rep before they waste time on a call that will be rejected.
- **Sample opt-in requiredness (SM-CALL-02/SM-OPT-01/02) is evaluated server-side only** (`SampleEligibilityService.cls:70-73`) — the iOS consent model (`ConsentRecord`, a fixed 3-year 21 CFR Part 11 validity window unrelated to sample opt-in) has no sample-specific opt-in-expiry concept to check against offline at all, so a rep cannot know in advance whether an HCP's opt-in has lapsed.

In short: **every rule that currently exists at all in this slice is server-side-only**; the client has, at most, one cosmetic (and non-authoritative) approximation of one of them. Building the "Shared Swift rules engine mirroring server rules" (SM-IOS-03, referenced by the build spec but outside my ID list) is a prerequisite most of these §10-13 IDs implicitly depend on for genuine offline-first behavior.

## 6. Reusable strengths and worst gaps

**Top reusable pieces found in this slice's scope:**
1. **`SampleEligibilityService.cls`** — a genuinely well-designed, single-point eligibility engine (product/license/opt-in/lot/limits) with FEFO lot assignment, hypnotic/sedative/tranquillizer blocking that already cites "UCPMP 2024 Clause 5.1(ii)(f)" verbatim, and cold-chain breach blocking. This is a strong foundation to extend rather than replace.
2. **`Call_Visit_Report__c.Signature_Image__c`'s ContentDocument-Id design** avoids the exact 32 KB truncation trap the spec warns about — reuse this pattern for the eventual real signature capture rather than RCPA's base64-LongTextArea approach.
3. **`ConsentCaptureView.swift` / `SignatureSheet`** — a real, working, in-person consent-plus-signature capture screen (channel toggles, live Canvas signature pad, 21 CFR Part 11 attestation copy) that is the closest existing precedent for SM-OPT-03 and, with real validation added, SM-SIG-05.
4. **`LocationService.swift`** — a working, sensible one-shot GPS fetch (25 s timeout, When-In-Use only) already used for call check-in; trivially reusable for SM-SIG-03's GPS stamp.
5. **RCPA's Personal Order Booking flow** (`RCPAViews.swift:762-820`, `POBLine`) — a structurally similar rep-initiated product+qty order UI, directly adaptable for SM-IO-01's Inventory Order lines, and `AccountsView.swift`'s search/filter pattern is a ready template for SM-IO-02.

**Top gaps/conflicts in this slice:**
1. **Barcode scanning is 100% absent** on both platforms (SM-BAR-01..09) — no VisionKit, no GS1 parsing, no matching logic, no activity log object. Entirely net-new, rated L across the board.
2. **Remote signing/opt-in has zero supporting infrastructure** (SM-SIG-09, SM-OPT-06..09) — no Experience Cloud/Site, no token scheme, no real push channel. The single largest build item in this slice.
3. **Cold-chain and custom-text fields exist on the object schema but are structurally unreachable from every UI that creates the parent records** (`cvrSampleDrops` LWC, `Sample_Transaction__c` layout) — a live CONFLICT, not just a future gap, since a cold-chain-flagged product would already fail every attempt to sample it through today's web form.
4. **Sample_Inventory__c (physical counts) does not exist at all** (SM-INV-01..07) — the entire §13 area is a from-scratch build; the closest existing artifact is a read-only admin discrepancy report over transactions, not a count workflow.
5. **The one sample-limit rule that is client-visible today is purely cosmetic and can diverge from the server's authoritative decision with no user-visible reconciliation** — see §5 above; this is the sharpest offline/online-parity risk in the whole slice, because it's not a *missing* feature but a *silently wrong* one already shipped.
