## 1. Architecture

- **Pattern: hand-rolled MVVM-ish, not textbook MVVM.** `Models/`, `Services/`, `Views/` are each flat directories (11, 25, 37 files respectively — no nested subfolders, no dedicated `ViewModels/` folder). `AccountStore` and `UserDataStore` are `@MainActor final class ... ObservableObject` with `@Published` properties that serve as the app's two central "ViewModel-like" stores; SwiftUI Views read/mutate them directly rather than via a per-screen ViewModel type. Evidence: `SciagenCRM/Services/AccountStore.swift:12-17`, `SciagenCRM/Services/UserDataStore.swift:14-15`.
- **Navigation: one `NavigationStack` inside a custom split layout — not `NavigationSplitView`, not `TabView`.** `ContentView.body` (the app shell) is a manual `HStack` of a custom `AppSidebar` (left rail, collapsible) + a single `NavigationStack(path: $path)` for the workspace. Evidence: `SciagenCRM/Views/RootView.swift:63-95`. Section switching is a plain `@State private var section: AppSection` enum driving a `@ViewBuilder switch` (`RootView.swift:17-24` enum, `:113-143` switch) — not tab- or stack-based. `.navigationDestination` is registered for three types (`Selection`, `CVR`, `SyncLogRoute`) on the one `NavigationStack` (`RootView.swift:90-92`); modals use `.fullScreenCover(item:)`/`.sheet(item:)` (`RootView.swift:97-110`).
- **Dependency injection: `@StateObject` at the app root, propagated via `.environmentObject`, consumed via `@EnvironmentObject`.** Evidence: `SciagenCRM/SciagenCRMApp.swift:27-28,46,50` (`@StateObject` for `salesforceAuth`, `store`, `userData`, `auth`), `:58-61` (four `.environmentObject(...)` calls), consumed at e.g. `RootView.swift:49-50,165-168`. One deliberate singleton exception: `CLMAssetDownloader.shared` (a background asset-download helper, not core state) — `SciagenCRMApp.swift:721-723`. `LocationService.shared` is also a singleton (`Services/LocationService.swift:16-17`).
- **Config switch is a single hardcoded flag.** `SciagenConfig.useLiveSalesforce = true` (`SciagenCRMApp.swift:18`) — the demo/mock path (`AuthStore` + `MockDataService`) is dead code as shipped; the live-Salesforce `AccountStore(service: SalesforceRestDataService(auth: auth))` construction is unconditional (`SciagenCRMApp.swift:39-41`), with the old ternary that allowed switching to `MockDataService` commented out (`:33-36`, marked "New code to Avoid demo mode by Aravindan").
- **Folder structure:** `SciagenCRM/{Models,Services,Views}` — no further subdivision by feature/module; feature area is signaled only by filename grouping (e.g. `CLMModels.swift`, `RCPAModels.swift`, `KAMModels.swift`, `ExpenseModels.swift`, `LeaveModels.swift`).

## 2. Persistence

- **Mechanism confirmed: Codable structs → one JSON blob → `UserDefaults`, NOT SwiftData/CoreData/Realm/SQLite/Mobile SDK SmartStore.** `UserDataStore.save()` builds a private `Blob: Codable` struct from every in-memory collection and encodes it via `JSONEncoder()`, then writes with `UserDefaults.standard.set(data, forKey: key)`. Evidence: `SciagenCRM/Services/UserDataStore.swift:1732-1757`. `load()` is the mirror: `UserDefaults.standard.data(forKey: key)` → `JSONDecoder().decode(Blob.self, ...)` (`UserDataStore.swift:1771-1774`, migration logic continues to ~1830s). File header states this explicitly: "Holds the current Sales Rep's private data and persists it locally (UserDefaults)" (`UserDataStore.swift:5-7`).
- **Storage key is namespaced per signed-in user**, not global: `private var key: String { "sciagen.repdata.v20.\(SyncScope.currentUserId)" }` (`UserDataStore.swift:128`) — so a second rep signing in on a shared device gets a separate blob. Sign-out wipes it: `UserDefaults.standard.removeObject(forKey: key)` (`UserDataStore.swift:1673-1676`).
- **`AccountStore.swift` itself holds no local persistence of HCP/HCO records** — it's an in-memory `@Published` store, with a *separate* on-disk cache delegated to `AccountCache.shared.load()/.save(...)` (called at `Services/AccountStore.swift:196-197,225,233-237`; `AccountCache.swift`'s own storage mechanism was not itself opened in this pass — UNVERIFIED, flagged above) and a delta-sync cursor via `SyncCursorStore` (UserDefaults-backed, see §3). `SalesforceRestDataService.swift`'s own header states there is **no offline cache at the network-service layer**: "There is no offline SmartStore or named-sync layer here... the HCP/HCO list is no longer available with no network connection" (`SalesforceRestDataService.swift:13-21`).
- **The `Sample_Drop__c`/`Sample__c` signature/consent stroke data is stored inside the same UserDefaults JSON blob** — flagged again under Security (§7), since `UserDataStore.swift`'s own comments (lines 1661, 1670) note the blob includes "signature strokes... consent records (incl. proof/signature data)".

## 3. Sync engine

- **Fetch (pull) pattern: a consistent "Updates" (delta, by known Salesforce Id) + "Discovery" (windowed or full pull) pair, per object family**, not a single unified delta engine. Examples confirmed by reading `AccountStore.swift`/`SalesforceRestDataService.swift`: `fetchCallVisitReportUpdates`/`fetchCallVisitReports`, `fetchLeaveRequestUpdates`/`fetchLeaveRequests`, `fetchRCPAAuditUpdates`/`fetchRCPAAudits`, `fetchDailyExpenseUpdates`/`fetchDailyExpenses`, `fetchMonthlyClaimUpdates`/`fetchMonthlyClaims`, `fetchAccountPlanUpdates`/`fetchAllAccountPlans`, `fetchConsentUpdates`/`fetchAllConsents`, `fetchSegmentationUpdates`/`fetchAllSegmentation`, `fetchDataChangeRequestDecisions`/`fetchDataChangeRequests` (see call sites throughout `SciagenCRMApp.swift:627-1069`, each wired into `syncAccounts()`).
  - HCP/HCO delta: `changedHCPIds(sinceDate:)` queries `Sciagen_Account__c`, `Affiliation__c`, `Publication__c`, `Congress_Event__c`, `Clinical_Trial__c`, `Account_Territory__c` all filtered by `LastModifiedDate >=` a cutoff, unions changed ids — `SalesforceRestDataService.swift:1749-1769`; falls back to a full unfiltered fetch when no cursor exists.
  - Windowed discovery pulls (e.g. Call Visit Reports) use an admin-configurable `Sync_Window_Days__c` (fallback 90 days) rather than pulling full history every sync — `AccountStore.syncWindowDays(objectApiName:fallback:)`, `AccountStore.swift:524-528`.
  - A periodic **forced full resync** (not just delta) is scheduled via `SyncCursorStore.shouldForceFullSync(for:intervalDays:)` (default `fullSyncIntervalDays = 7`, `AccountStore.swift:114,183`) — read in full, `Services/SyncCursorStore.swift` (56 lines): per-object cursor (`Date`) stored in `UserDefaults.standard` keyed `"sciagen.synccursor.<userId>.<objectKey>"` (lines 18,24-26,35-37).
- **Push (submit) methods** cover every rep-owned object family: `submitCallVisitReport`, `submitRCPAAudit`, `submitDailyExpense`, `submitMonthlyClaim`, `submitAccountPlan`, `submitConsent`, `submitSegmentation`, `submitLeaveRequest`, `submitPlannedCall`, `submitDataChangeRequest`, `submitSyncTracking`, `submitCustomList`/`submitCustomListMember`, `submitSavedView`, `submitSyncLogToSupport`, `submitDeviceResetRequest` — implemented in `SalesforceRestDataService.swift` and each wrapped by a matching `push*` static function in `SciagenCRMApp.swift:288-461`.
- **No formal outbox/queue table** — "unpushed" is simply any local record whose `salesforceId == nil`. `SciagenCRMApp.retryUnsyncedPushes(store:userData:)` iterates every local collection filtering on that, capped at `maxPushesPerTypePerSync = 20` records per type per sync cycle (deliberate bound — see doc comment, `SciagenCRMApp.swift:549-559`) — evidence: `SciagenCRMApp.swift:561-602`.
- **Idempotency:**
  - Parent records: `createOrUpdate(path:existingId:jsonBody:)` PATCHes if a local `salesforceId` is already known, else POSTs and captures the new Id — every `submit*` routes through this, so a retried save updates rather than duplicates. Evidence: `SalesforceRestDataService.swift:2805-2821`.
  - Child records (CVR attendees/key messages/promo/sample drops): `CVR.syncedChildIds: Set<String>` tracks keys like `"sample:<SampleDrop.id>"` so a retried CVR push skips children already confirmed synced — model field `CLMModels.swift:369-378`; enforced in the push loop, e.g. `SalesforceRestDataService.swift:2453-2455` (`guard !cvr.syncedChildIds.contains(key) else { continue }`).
  - No idempotency-key HTTP header is sent; idempotency relies entirely on the above local-state pattern.
- **Retry logic:** per-record cap `SciagenConfig.maxAutoRetryAttempts = 5` (`SciagenCRMApp.swift:18-22`), tracked via `userData.failedSyncAttemptCount(localRecordId:)`; beyond that a record is treated as "permanently stuck" and stops being auto-retried (rep can force a fresh attempt by editing/resubmitting). No exponential backoff — a failed push simply waits for the next sync cycle (launch, or manual "Sync Now"). Evidence: `SciagenCRMApp.swift:561-601`.
- **Conflict handling:** no HTTP 409-specific branch exists — any non-2xx response (including 409) throws a generic `SalesforceDataServiceError.httpError`. Only 401 is special-cased (token refresh + retry). A `Conflict_Resolution__c` field is read as metadata from `Sync_Object_Config__mdt` (`SalesforceRestDataService.swift:46-64`) but the client's own doc comments describe the effective policy as "Salesforce always wins" on pull-back — i.e., conflict resolution is a one-directional overwrite on pull, not a client-side merge algorithm (comments at e.g. `UserDataStore.swift:187,626,771,848,979,1106,1286`).
- **Auto-sync-on-save (confirmed, not inferred):** every user-facing local save method calls `save()` then synchronously invokes the matching `on*Changed?` hook, e.g. `saveCVR` → `onCVRChanged?(cvr)` (`UserDataStore.swift:589`); `saveConsent` → `onConsentChanged?` (`:1275`); similarly for RCPA (`:738`), Daily Expense (`:834`), Monthly Claim (`:900`), Leave (`:966`), Account Plan (`:1052`), Planned Call (`:1417/1419/1428`), Segmentation (`:175`). `SciagenCRMApp.configureAutosync()` (`SciagenCRMApp.swift:194-240`) wires each hook to a `Task { await pushX(...) }` call, so **every local write reaches Salesforce as soon as it happens**, not only on a final "Submit."
- **No repeating background timer** — deliberately removed. Doc comment: an earlier 60-second timer "mirrored a fresh Sync_Tracking__c row on every tick... and retried permanently-broken local records forever, both without bound, and together exhausted this org's data storage limit" (`SciagenCRMApp.swift:147-158`). Sync instead runs once at launch (`.task { await runLaunchSync() }`, `SciagenCRMApp.swift:72`) plus on-demand via a manual "Sync Now" (`Views/HomeView.swift:325-350`, confirmed to duplicate — not call — `runLaunchSync`'s pipeline logic). No `BGTaskScheduler`/`BGAppRefreshTask` registration exists anywhere in the codebase (grep confirmed zero matches) — there is no iOS background-refresh capability configured.
- **Sync scoping: per-user (device-local cache/cursor namespacing) + territory-based (server-side record visibility).** `SyncScope.swift` (28 lines, full read) holds a single `currentUserId: String` (default `"anonymous"`), set by `SalesforceAuthService` on init/login/refresh/logout, and used to namespace both `UserDataStore`'s UserDefaults key (§2) and `SyncCursorStore`'s cursor keys. Actual **data visibility** is territory-based at the Salesforce/SOQL level: HCP/HCO territory assignment comes from a junction object `Account_Territory__c` (`Territory__c` lookup), joined in `fetchHCPs`/`fetchHCOs` via `mapTerritoryAssignments` (`SalesforceRestDataService.swift:1866-1879`); `CVR.territory` resolves a `Territory__c` Id via `resolveTerritoryId(named:)` (`SalesforceRestDataService.swift:2384-2386,2663`). A doc comment states directly: "Territory-based sharing on the Salesforce side means 'visible to this rep' IS the rep's assigned territory" (`UserDataStore.swift:421-426`). The actual Salesforce sharing-rule enforcement is server-side and not visible in this client code.
- **Sync log (audit trail):** `UserDataStore.syncLog: [SyncLogEntry]`, rendered in `Views/SyncLogView.swift` (299 lines, full read) with filter pills (All/Pending/Synced/Failed/Skipped/Deleted) covering every `SyncRecordType` (DCR, CVR + 5 child types, Accounts, Leave, RCPA audit/line/POB line, Daily/Monthly Expense + patch/bill, Account Plan + strategy/stakeholder/team/goal, Consent, Planned Call, Segmentation, Presentation, My Alerts, Custom List, Saved View) — evidence: `SyncLogView.swift:210-241`. Supports "Upload to Support" (JSON-encodes the log + device/app metadata, submits as a Salesforce Case attachment via `submitSyncLogToSupport`) — `SyncLogView.swift:87-113`. Retention capped at `maxSyncLogEntries = 500` locally (`UserDataStore.swift:442`) and pruned server-configurably (`store.syncLogRetentionDays(fallback: 30)`, `SciagenCRMApp.swift:169`). Each entry can optionally mirror to a Salesforce `Sync_Tracking__c` record via a per-entry serialized push queue that prevents duplicate mirror-creates on rapid Pending→Synced transitions (`SciagenCRMApp.swift:463-527`).

## 4. Auth

- **OAuth flow: Authorization Code + PKCE, custom-built (no Salesforce Mobile SDK), via `ASWebAuthenticationSession`.** File header states this directly: `Services/SalesforceAuthService.swift:5-11`. PKCE verifier/challenge (SHA-256) generation at `:425-433`; `/authorize` URL built with `code_challenge`, `code_challenge_method: S256`, `state` (`:295-311`); code exchanged at `/services/oauth2/token` with `code_verifier` (`:352-380`); session presented via `ASWebAuthenticationSession` with `prefersEphemeralWebBrowserSession = true` (`:326-347`); refresh-token flow (`grant_type: refresh_token`) with a single-flight guard (`inFlightRefresh`) to avoid concurrent-refresh races (`:83-90,265-291,382-400`). Not a username/password flow (no `grant_type: password` anywhere). Custom URL scheme for the OAuth redirect: `com.sciagen.crm` (`Info.plist:24-29`); login host is a sandbox org, `allergo-pharma--dev.sandbox.my.salesforce.com` (`Info.plist:42-43`). The OAuth consumer key is a **hardcoded string literal in source** (`SalesforceAuthService.swift:26`, with a second, commented-out key at `:28`) — standard practice for a Salesforce Connected App's public client id, but worth noting as a literal committed to source control.
- **Token storage: genuine iOS Keychain usage, not UserDefaults.** `KeychainStore` (a private enum) wraps `SecItemAdd`/`SecItemCopyMatching`/`SecItemDelete` against `kSecClassGenericPassword`, storing a JSON blob of `{accessToken, refreshToken, instanceURL, userId}` as `kSecValueData` — `SalesforceAuthService.swift:502-566`. Accessibility is explicitly `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (excludes iCloud Keychain/encrypted-backup sync) — `:533`. A fresh-install guard clears stale Keychain entries (since Keychain survives app deletion, unlike UserDefaults), gated by a UserDefaults marker flag — `:103-120`.
- **Session timeout / biometric re-auth: none found.** Exhaustive grep for `LAContext`, `biometry`, `Face ID`/`FaceID`, `Touch ID`, `LocalAuthentication`, `sessionTimeout`, `idleTimeout`, `autoLock` returned zero matches anywhere in the codebase, and `Info.plist` was confirmed to have no `NSFaceIDUsageDescription` key. The only session-expiry handling is OAuth access-token expiry via `recoverFromUnauthorized()` (401 → refresh-token attempt → forced re-login on failure) — `SalesforceAuthService.swift:265-291`.
- **Sign-out discrepancy worth flagging:** `SalesforceAuthService.logout()` clears in-memory tokens + Keychain + `SyncScope`, but the step that would additionally end the Salesforce SSO browser cookie server-side is **commented out** (`SalesforceAuthService.swift:205,212`, tagged "by Aravind"), while the surrounding doc comments (`:198-214`) still describe that as the intended behavior. As shipped, signing out of the app does not invalidate the SSO session in the device's web view.
- **Sign-out does NOT wipe local data** — deliberate, per doc comment at `RootView.swift:279-285` (data stays on-device across sign-out/sign-in of the same user).

## 11. Client-side validation/business rules that duplicate (or may duplicate) server-side logic

All of the following are computed and enforced **only in this iOS client** — no Apex/server code was available to this audit (client-only repo), so **each is flagged as needing a cross-check against the Salesforce org's Apex triggers / validation rules** before assuming server-side parity exists.

1. **Yearly UCPM (units-cap-per-year) sample limit — hardcoded to exactly 3 products.** `Services/CLMData.swift:20-32`: Emrok 48/yr, Glaritus 36/yr, Miqnaf 60/yr. Any other live-catalog product has **no limit at all** (`yearlyLimit` → `nil`, UI shows "No yearly limit configured for X"). This is a genuinely hardcoded, client-local rule with no corresponding field on the live `Product__c` object (per the code's own comment, `CLMViews.swift:810-814`). **Needs cross-check**: does `Sample_Drop__c` have an Apex trigger enforcing an equivalent (or any) yearly cap per HCP × Product?
2. **The yearly-usage count itself is local-device-only** (`UserDataStore.samplesUsedThisYear`, `UserDataStore.swift:663-669`) — sums only CVRs already present in the on-device array; can under-report (and therefore under-enforce) if the device's local history is incomplete. **Needs cross-check**: is there a server-side aggregate check that would catch what the device misses?
3. **The cap is UI-advisory only, not a hard save/submit gate.** The "over limit" flag on already-added rows is cosmetic (red icon/text) and does not block `save()`/`submit()` (`CLMViews.swift:1050-1070`); the add-new-sample stepper/button are capped, but this is pure SwiftUI state — trivially bypassable by any client calling the same REST endpoint directly, and the push payload itself (`CVR__c/Product__c/Qty__c` only, `SalesforceRestDataService.swift:2446-2469`) shows no evidence this client expects or checks for a server-side rejection of an over-limit quantity.
4. **No cross-device/cross-rep race protection** — two devices computing `remaining` independently (each from their own possibly-stale local cache) could each push a quantity that individually looks within-limit but jointly exceeds it, with no observed conflict/limit check on the push side.
5. **RCPA's Personal Order Booking (POB) has zero quantity governance** — a flat `1...500` stepper range (`RCPAViews.swift:807` per the screens-audit pass), no yearly/quota logic whatsoever, unlike Samples. Flagged in case POB is ever treated as sample-adjacent inventory by the business.
6. **Call backdate limit** — `store.callBackdateLimitDays` (default 30, `AccountStore.swift:30`) resolved from a **server-configured** Hierarchy Custom Setting (`Call_Backdate_Limit__c`, fetched via `service.fetchCallBackdateLimitDays()`, `AccountStore.swift:259`) and enforced client-side as `isBackdateOutOfRange`/submission-cutoff gating in `CallReviewView` (`CLMViews.swift:1153-1194`) and reused for CVR-editability in `RootView.isCVREditable` (`RootView.swift:145-156`). Unlike the sample-limit rule, this one is client-enforced but server-sourced — still worth a cross-check that Salesforce itself also rejects a late-backdated submission rather than relying solely on the app not allowing it.
7. **Daily email send limit** — `dailyEmailLimit = 50` hardcoded client-side (`UserDataStore.swift:1354`), gating `ApprovedEmailComposer`'s send button (`canSendEmailToday`, `:1358`). Not sample-related, but the same "hardcoded client cap, no confirmed server mirror" pattern — flagged for completeness.
8. **DCR "HCP must be affiliated with an existing HCO"** — enforced client-side in the New Account Request form per `DCRView.swift:5-7`'s own header comment ("Enforces: an HCP must be affiliated with an existing HCO"); not independently verified against Apex.
